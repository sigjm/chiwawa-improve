# 증거 기반 후보 적용 — 변경 전·후 검증 기록

- 작성일: 2026-10-07
- 기준(변경 전): `develop` @ `fab6abd`
- 1차 개선: `1f426dc` (1~6절)
- 2차 개선: 이 문서가 포함된 커밋 (7절). 1차에서 남긴 항목을 이어서 처리했습니다.
- 변경 내용 설명: [`../README.md`](../README.md)의 "증거 기반 후보" 절

사진 장소 검색에 [Oldcircle/geo-sleuth](https://github.com/Oldcircle/geo-sleuth)의 원칙(위치 prior, 동명 후보 순위화, 읽은 글자 폴백, 위치 힌트 주변 탐색)을 옮긴 뒤, 같은 입력에서 결과가 어떻게 달라졌는지와 결함이 실제로 고쳐졌는지를 확인한 기록입니다.

## 먼저 읽을 것: 이 기록이 말하는 것과 말하지 않는 것

- **실사진·실 API로 측정한 정확도가 아닙니다.** 작업 환경에 Google API 키가 없어 Cloud Vision·Gemini·Places를 실제로 부르지 못했습니다.
- 아래 위치 비교는 **고정 시나리오 재생**입니다. Vision·Gemini 출력은 시나리오에 적어 둔 값이고, Places는 [`scripts/replay_scenarios.py`](../scripts/replay_scenarios.py)의 `SimPlaces`가 흉내 냅니다. 변경 전·후 코드에 **같은 입력**을 넣었을 때 후보 선택 로직의 차이만 보여 줍니다.
- `SimPlaces`는 두 가지 사실에 기대고 있습니다. 둘 다 Google Text Search 문서에서 확인했습니다.
  - `locationBias`·`locationRestriction`을 모두 생략하면 **호출 서버의 IP 위치**로 결과가 편향된다.
  - `locationBias`는 제한이 아니라 편향이다.
- 가정도 있습니다. 서버 IP 위치를 미국 동부로 두었고(실제 Modal 리전은 확인하지 못함), 동명 장소 일부(`가상` 표기)는 상황을 만들려고 넣었습니다. 실제 Places의 순위는 이보다 복잡합니다.

실제 정확도를 알려면 키를 넣고 `scripts/run_image_search.py`로 실사진을 돌려야 합니다.

## 3. 고쳐지지 않은 것

> 1차 시점의 목록입니다. **✅ 표시는 2차에서 해결했습니다(7절).**

- ✅ **좌표 prior가 없는 체인점 (시나리오 8).** Places가 서버 IP 근처 지점만 5건 돌려주면 여행 국가 우선 정렬이 할 일이 없습니다. 여행지 좌표를 넓은 `locationBias`로 넘기면 풀리지만, 여행에 좌표가 저장돼 있지 않고 요청 계약에 필드를 추가해야 해서 이번 범위에서 뺐습니다. 다음 개선 1순위입니다.
- ✅ **여행 국가 표기 불일치 (시나리오 7).** (여행에 도시가 있을 때. 국가만 있으면 그대로 남음) "일본"과 "Japan"을 같은 나라로 보지 못합니다. Places `addressComponents.shortText`(ISO 코드) 비교로 바꾸면 됩니다.
- **같은 나라·같은 도시 안의 지점 구분 (시나리오 6, 9).** (2차에서 도시까지는 좁혀짐. 같은 도시 안의 지점 구분은 그대로) 여행 도시는 글자 폴백의 검색 범위로만 쓰고 순위에는 쓰지 않습니다. 당일치기처럼 여행 도시 밖의 장소를 찍은 사진을 밀어내지 않기 위한 선택입니다.
- **지역만 알려 주는 글자.** 주소판이나 안내판의 관리 주체(〇〇警察署 등)를 위치 prior로 쓰지 않고, 장소 이름처럼 검색합니다.
- ✅ **화면에 근거가 보이지 않음.** (`reason` 표시. `category`는 Backend 응답에 없어 그대로) 후보의 `reason`("사진 속 글자 … 로 검색한 장소", "같은 이름으로 검색된 다른 장소")은 Backend까지 전달되지만 Flutter가 읽지 않습니다(`api_photo_place_repository.dart`, `category`도 빈 문자열로 고정).
- **Gemini 프롬프트 변경은 실호출로 확인하지 못했습니다.** `visible_text`를 이름일 가능성이 높은 순으로 나열하라는 한 문장을 추가했는데, 실제 출력이 그렇게 정렬되는지는 측정하지 않았습니다.

## 7. 2차 개선 (2026-10-07)

1차에서 남긴 네 항목을 이어서 처리했습니다.

| 남은 항목 | 처리 | 결과 |
|---|---|---|
| 실 API 측정 | **못 했습니다.** 작업 환경에 Google API 키가 여전히 없습니다 | 아래 수치도 시뮬레이션입니다. Gemini 프롬프트 변경도 실호출 미확인 상태 그대로입니다 |
| 좌표 없는 체인점 | 랜드마크 앵커·촬영 좌표가 없고 여행 도시가 있으면, "도시 국가"를 Places에서 한 번 찾아 그 좌표를 반경 20km의 위치 prior로 사용 | 시나리오 6·7·8 개선 |
| 화면 표시 | Flutter `PhotoSearchResult`에 `reason` 추가, 결과 카드와 후보 목록에 근거 문구 표시. 빈 카테고리 칩은 숨김 | 위젯 테스트 2건 추가 |
| 동명 후보로 인한 동작 변화 | 기본값(2개)은 유지하고, 환경변수 `IMAGE_SEARCH_MAX_ALTERNATIVES`로 조절·해제(0) 가능하게 함 | 테스트 3건 추가 |

1차 보고에서는 여행지 좌표를 쓰려면 요청 계약에 필드를 추가해야 한다고 적었지만, 모듈 안에서 여행 도시를 직접 조회하는 더 작은 방법이 있어 그쪽으로 구현했습니다. 대신 해당 요청마다 Places 호출이 1회 늘어납니다.

함께 넣은 것:

- **시간 예산.** 선택적인 Places 호출(여행지 좌표 조회, 글자 폴백)은 요청 시작 후 60초 안에만 시작합니다. 외부 호출이 전부 timeout 나는 최악의 경우 소요 시간이 1차에서 120초(URL 입력 기준, Modal 한도와 같음)까지 늘 수 있었는데, 이것을 원래 코드와 같은 100초로 되돌렸습니다.
